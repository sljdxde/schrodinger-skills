# Interview Engine v2 — 第一性原理访谈引擎

v1 只问了「目标 / 能力 / 边界」三件事，缺口很大：输出是 md 还是 html、输入从哪来、分析维度怎么定、交互几轮、受众是谁、要不要联网/凭证——这些决定一个 Skill 长什么样的第一性维度全被漏掉了，只能临场补。

v2 的做法：**先把一个 Skill 必须被定义清楚的维度拆全（第一性原理），再把每个维度做成「一簇问题 + 决策树分支」，一次问一片，而不是一次问一个。** 访谈目标不是礼貌地收集信息，而是逼出用户自己都没意识到的需求。

---

## 0. 第一性原理：一个 Skill 必须被定义清楚的 10 个维度

不管理由多花哨，一个可安装的 Agent Skill 本质是一个能力黑盒：

> **（某类用户）** 在 **（某场景）** 下，给 Skill **（某些输入）**，它用 **（某方法）** 处理，产出 **（某种形态的输出）**，受 **（边界）** 约束，依赖 **（知识/数据）**，以 **（某种交互方式）** 运作，用 **（某标准）** 判断是否做好了。

把这拆成 10 个维度（F0–F9），缺任何一个，生成的 Skill 就会「跑偏」或「答非所问」：

| # | 维度 | 第一性提问 | 漏掉会怎样 | → blueprint 字段 |
|---|---|---|---|---|
| F0 | 身份与触发 | 它叫什么？什么场景下该被唤醒？ | description 空泛，不会自动触发 | `name` `description` `trigger` `intro` |
| F1 | 用户与场景 | 谁用？什么水平？在哪用？多频繁？ | 语气/解释深度错配 | `audience` `intro` |
| F2 | 目标与任务类型 | 它的核心 job 是什么？生成/分析/决策/自动化/问答/流程？ | 能力清单跑题 | `capabilities` `workflow` |
| F3 | 输入与数据来源 | 输入从哪来？要哪些？缺了怎么办？ | 不知道要问用户要什么 | `input_spec` |
| F4 | 流程与方法 | 分几步？深度/严谨度几档？用哪些工具？ | workflow 空洞 | `workflow` `principles` |
| F5 | 分析框架 ⚠️条件 | 分析哪些维度？怎么打分？证据多严？要不要对比/可视化？ | 分析型 skill 没有骨架 | `analysis` |
| F6 | 输出规格 ⚠️条件 | 产出是 md / html / json / 对话 / 多文件？结构多长？语气？ | 用户想要报告却给了一句话 | `output_spec` |
| F7 | 边界 | 包含/不包含？绝对不做的？ | Skill 失控或预期落差 | `boundaries` |
| F8 | 知识与外部数据 | 需要哪些参考资料？联网/API/凭证？ | 凭空编造 | `references` `data_sources` |
| F9 | 交互与质量 | 一轮给完还是多轮澄清？不确定时问还是猜？怎么算成功？ | 不该问的瞎问 / 该问的不问 | `interaction_model` `evaluation_criteria` |

⚠️ F5、F6 是**条件维度**：只有当该 Skill 是「分析/决策」型（F2 命中）才深挖 F5；只有当它有「产出物」时才深挖 F6。其余 8 个维度**每个 Skill 都要过**。

## 1. 路径分流（保留并细化）

收到请求后先用一句话判断路径，决定访谈起点：

| 信号 | 路径 | 起点 |
|---|---|---|
| 「我想做一个 XXX 助手」「帮我建个 XXX 工具」——有需求说不清能力 | **Path A：Need → Skill** | F0 → F1 → F2 … |
| 「我干 XXX 二十年」「我有一套 XXX 方法论想沉淀」「我的经验想变成数字资产」 | **Path B：Experience → Skill** | 经验建模 → 映射到 F2/F3/F4/F5 |
| 两者都不明显 | 先问 F0+F2 一句：「你希望它帮你解决什么问题，还是把你已有的经验/流程固化下来？」 | 按回答进 A 或 B |

Path B 不单独搞一套问题，而是把「经验」映射到同一张维度表：案例 → F3 输入、判断规则 → F4/F5、踩坑 → F7 边界与 F9 错误处理。这样 A/B 殊途同归，蓝图结构统一。

## 2. 决策树总览

```
START
  │
  ├─ F0 身份与触发        （名称 / 一句话描述 / 触发场景）
  │
  ├─ F1 用户与场景        （使用者 / 水平 / 使用位置 / 频率）
  │
  ├─ F2 目标与任务类型    （核心 job / 任务类型：生成·分析·决策·自动化·问答·流程）
  │        │
  │        ├─ 类型 ∈ {分析, 决策} ──► F5 分析框架【必问】
  │        └─ 类型 ∈ {生成, 自动化, 流程} ──► 跳过 F5，但 F6 照常
  │
  ├─ F3 输入与数据来源    （渠道 / 格式 / 必填 / 选填 / 缺失行为）
  │
  ├─ F4 流程与方法        （步骤 / 深度档位 / 工具调用）
  │
  ├─ F6 输出规格          （只要「有产出物」就必问：格式 / 结构 / 长度 / 语气 / 交付物）
  │        │
  │        ├─ 格式 = HTML/交互 ──► 追问：是否要交互（折叠/表单/图表）？单文件还是多资源？
  │        ├─ 格式 = 多文件/下载 ──► 追问：文件名/目录约定？要不要打包？
  │        └─ 格式 = 对话直答 ──► 追问：要不要附结构化摘要？
  │
  ├─ F8 知识与外部数据    （参考资料 / 联网 / API / 凭证）
  │        │
  │        └─ 需要 API/凭证 ──► 追问：哪个服务？key 怎么给？有无限频/费用？
  │
  ├─ F9 交互与质量        （一轮/多轮 / 澄清风格 / 不确定时问还是猜 / 成功判据）
  │        │
  │        └─ 受众 = 新手 ──► 追问：要不要术语表/逐步解释？
  │
  ├─ F7 边界              （包含 / 不包含 / 绝对不做）← 收口，永远最后
  │
  ▼
BLUEPRINT（落到 blueprint.json，见 blueprint-schema.md）
```

**关键分支纪律**：
- **有产出物 → F6 必问**，且按格式再下钻（HTML 问交互、多文件问命名）。
- **分析/决策型 → F5 必问**，且必须落到具体维度、打分方式、证据严谨度。
- **要联网/API → F8 必问凭证**，避免生成出"需要 key 却没设计怎么拿"的半成品。
- **受众=新手 → F9 补术语处理**，避免输出满篇黑话。

## 3. 分面访谈脚本（每面一簇问题）

每面一次抛出 **3–6 个**问题（多选 + 开放混合），不逐条追问；只有「缺了会改变化身」的才问。已能从上下文推断的，直接列为假设并请用户确认，不要浪费一轮。

### F0 · 身份与触发（每 Skill 必问）
1. 这个 Skill 你想叫什么名字？（给 2–3 个候选 slug，如 `house-advisor`）
2. 用一句话描述它「干什么、帮谁」？（用于 `description` 的 "Use when..." 起头）
3. 用户在什么情况下会用到它？（触发场景，如「想买房但不知从何下手时」）
4. 它是独立工具，还是某个更大流程里的一环？（影响 `trigger` 写法与边界）

### F1 · 用户与场景（每 Skill 必问）
1. 主要给谁用？—— 自己 / 团队同事 / 外部客户 / 公众
2. 使用者的领域水平？—— 小白 / 有一定基础 / 专家（决定解释深度与术语密度）
3. 主要在哪用？—— 桌面对话 / 手机远程 / 嵌在工作流里 / 批量跑
4. 使用频率？—— 一次性 / 周期性 / 长期常开（影响是否需要「自检更新」与持久化）

### F2 · 目标与任务类型（每 Skill 必问）
1. 它的核心 job 是什么？（用户要它「做完」的那件事）
2. 任务类型最接近哪类？【多选】生成 / 分析 / 决策建议 / 流程自动化 / 问答 / 多步编排
3. 怎么算「它帮你做好了」？（成功判据的雏形，喂给 F9）
4. （若多选了多个类型）以哪个为主？次要类型做浅还是做深？

### F3 · 输入与数据来源（每 Skill 必问）
1. 输入从哪来？【多选】用户打字 / 上传文件(图片·PDF·表格) / 给网页链接抓取 / 调用 API / 读本地文件 / 无需输入
2. 必须提供的信息有哪些？（必填项；缺了就不能开工的）
3. 可选补充的信息有哪些？（选填项；有则更准，无也能跑）
4. 关键信息缺失时怎么办？—— 先追问 / 给默认值继续 / 直接拒绝
5. 输入可能是什么格式？（text / image / pdf / csv / json / audio / video）

### F4 · 流程与方法（每 Skill 必问）
1. 它处理这件事分几步？（把 workflow 先捋出来）
2. 处理深度分几档？—— 快速版 / 标准版 / 深度版（是否按用户输入切换）
3. 需要调用哪些外部能力？【多选】联网搜索 / 跑代码 / 读文件 / 调 API / 纯推理 / 生成图片或图表
4. 领域内有什么「必须遵守的方法/铁律」？（变成 `principles`）

### F5 · 分析框架（⚠️ 仅当 F2 ∈ {分析, 决策} 时必问，否则跳过）
1. 要从哪几个维度/方面分析？（如户型：空间利用·动线·采光通风·私密性·改造潜力）
2. 结论要不要量化打分？—— 不打分(定性) / 二分(是否) / 量表(1–5) / 加权评分卡
3. 证据严谨度要求？—— 自由发挥 / 必须标来源 / 必须给置信度 / 拿不到写「未查到」不许编
4. 要不要对标/对比？（与同类比 / 与历史比 / 不需要）
5. 要不要可视化？（结构表 / 评分卡 / 图表 / 流程图 / 不需要）
6. 有没有行业公认框架/模型必须套用？（如 SWOT、波特五力、ROI 模型）

### F6 · 输出规格（⚠️ 只要「有产出物」就必问）
1. 主要交付物是什么形态？【单选为主】Markdown 报告 / HTML 交互页 / JSON 结构化 / 对话直答 / 多文件包 / 可下载文件
2. 报告/产出要有哪几块结构？（概览 / 分维度 / 评分卡 / 建议清单 / 优缺点 / 引用）【多选】
3. 篇幅与详略？—— 一句话结论 / 精简 / 详细 / 详尽带论证
4. 语气与语言？—— 正式专业 / 通俗带解释 / 轻松口语；中文 / 英文 / 双语
5. 要不要产出可下载文件？文件名/目录怎么约定？（如 `output/<小区><面积>分析报告.md`）
6. （若选了 HTML/交互）要不要交互能力？—— 折叠展开 / 表单输入 / 动态图表 / 单文件还是多资源
7. （若选了 JSON/结构化）字段 schema 谁定？—— 你给范例 / 我来建议 / 套某个标准

### F7 · 边界（每 Skill 必问，且永远收口在最后）
1. 它**明确该做**哪些？（从 F2/F4 收敛出 include）
2. 它**明确不做**哪些？（exclude；尤其用户「以为它会做但其实不该做」的）
3. 有没有绝对红线？—— 不替用户做业务决策 / 不编造来源 / 不触碰隐私 / 不执行破坏性操作
4. 逐条确认 exclude 里有没有用户预期内的事（防预期落差）

### F8 · 知识与外部数据（每 Skill 必问）
1. 它需要哪些领域参考资料/手册？（生成 `references/` 的 stub 清单）
2. 要不要联网查实时信息？（房价/天气/法规等会变的）
3. 要不要调第三方 API？—— 哪个服务 / key 怎么提供 / 有限频或费用吗
4. 有没有用户私有的知识要「喂」进去？（文档/表格/历史案例）

### F9 · 交互与质量（每 Skill 必问）
1. 交互模式？—— 一轮给全 Input→直接出结果 / 开工前先问清一簇问题 / 边做边确认
2. 澄清风格？—— 一次性问整簇 / 按需逐个问 / 绝不问（直接假设并标注假设）
3. 不确定时怎么办？—— 明确追问 / 给最佳猜测并标「不确定」/ 拒绝回答
4. 成功判据怎么写进自测？（喂给 `evaluation_criteria`，如任务成功率、错误率）
5. （若 F1 受众=新手）要不要内置术语表/逐步解释？

## 4. 决策树分支规则速查

| 条件（来自前面回答） | 必须追加的追问 |
|---|---|
| F2 含「分析」或「决策」 | F5 全问；且 F4 必须给出「判断依据」 |
| F6 格式 = HTML/交互 | F6.6 交互能力；是否单文件 |
| F6 格式 = 多文件/下载 | F6.5 文件名/目录约定 |
| F8 需要 API | F8.3 服务名 / key 提供方式 / 限频费用 |
| F8 需要联网 | F8.2 实时信息类型 + 来源标注规则 |
| F1 受众 = 新手 | F9.5 术语表；F4 解释深度上调 |
| F2 多类型 | F2.4 定主类型，次要类型定深浅 |
| 用户一次性给足目标+场景+边界 | 其余缺口列为「假设」请确认，直接进蓝图 |

---

## 5. 通用纪律

- **一次问一片，不一次问一个**：每面 3–6 题成簇抛出；靠分支下钻，不靠来回拉锯。
- **10 维度全覆盖**：F0–F4、F7–F9 每个 Skill 必过；F5/F6 按条件触发但触发后必问全。
- **已经能推断的就别问**：直接列为假设请用户确认，省一轮。
- **不要绕过访谈**：不要用「我先分析一下」替代需求采集；访谈本身就是价值。
- **跑题就拉回**：温和重复当前面的问题，不陪聊。
- **收敛**：所有面走完后，给用户看一遍蓝图摘要（含 10 维度要点），确认再进 Compiler。
